# agy-switchの保守性・性能・安定性を改善する計画

本プロジェクトは [ZhangNy301/agy-switch](https://github.com/ZhangNy301/agy-switch) を参考にしている。

まず通信と保存処理の失敗を制御できるようにし、その後、キャッシュの読み込みとAPI取得を最適化する。速度の改善はベンチマークで確認し、認証情報の保持と既存コマンドの動作を各変更の完了条件にする。

計画した6項目の変更を実装した。Linux・macOS・Windowsのamd64環境で、テスト・競合検査・バイナリ起動確認が成功した。配布方法はGoバイナリに統一した。

## 実装後の性能と検証結果

キャッシュは一括で読み、更新されていなければ解析済みの内容を再利用する。認証の変更はプロセス間ロックで直列化し、失敗時は変更前の情報への復元を試みる。復元できない場合はエラーを返し、復旧用ジャーナルを保持する。中断された変更も、次のアカウント操作で復旧を試みる。

CLIは用途ごとのファイルへ分割した。`root.go` は460行から118行になり、認証ストア・HTTPクライアント・プロセス実行をテストから差し替えられる。テストでHTTPのグローバル変数を書き換える処理は除去した。

次の値は、ビルドや他のテストを止めて3回測った中央値である。時間と割り当て量の単位を分けて示す。

| 測定条件 | 処理時間 | 1回あたりの割り当て量 | 割り当て回数 |
| --- | --- | --- | --- |
| キャッシュ再利用・10アカウント | 0.002904ms | 約4.56KB | 22回 |
| キャッシュ再利用・100アカウント | 0.017002ms | 約36.3KB | 118回 |
| 新しいクライアント作成と初回読込を含む・100アカウント | 0.137681ms | 約96.9KB | 243回 |

100件の初回読込を含む測定でも、当初の目標1〜5ms・0.1〜0.5MBを下回った。後述の旧参考値は同時ビルド中の測定であり、厳密な同条件比較ではない。いずれもモデル初期化の測定で、画面描画、実APIの待ち時間、CLI起動全体は含まない。

各応答に100msの遅延を加えた模擬APIでは、3リクエストの逐次取得が301.662ms、並行取得が100.869msだった。待ち時間は約3分の1になった。一方、この条件での割り当て量は約76KBから約104KBに増えた。並行化には一時的なメモリ増加が伴うため、同時HTTP処理数の既定値を4に制限した。実際のGoogle APIでの短縮幅は未測定である。

通信全体の期限は既定15秒とし、OAuth更新と再試行の待機も含める。`--quota-timeout` と `--quota-concurrency` で調整できる。同じアカウントへの同時呼び出し12件を、模擬条件で1回分のAPI取得3リクエストへまとめることも確認した。

公開時のGitHubの検査でOAuthクライアントの埋め込み定数が検出されたため、設定を外部化した。トークンの更新には、環境変数 `AGY_SWITCH_OAUTH_CLIENT_ID` と `AGY_SWITCH_OAUTH_CLIENT_SECRET`、またはデータディレクトリの `oauth_client.json` が必要になる。設定の欠落・不備は通信前に検出し、保存済みのクォータ表示は維持する。既存のローカル履歴は保持し、検出された定数を含まない公開用ブランチを作成した。

Linux上で70テストと競合検査が通過した。保存容量不足に相当するエラー、認証ストアの拒否、ログイン中断、復旧用ジャーナルの保存失敗と復元、キャッシュの競合更新、別プロセスとのロック競合、OAuth設定と更新を検査している。ブリッジは1,000接続の解放、半切断、待機中の停止、プロキシ変更後の新旧接続の扱いを確認した。

6対象のリリース用バイナリに加え、macOS arm64向けのテストコードもコンパイルできた。[OS別CIの実行結果](https://github.com/cwatanab/agy-switch/actions/runs/44107314892)では、Linux・macOS・Windowsのamd64で競合検査とバイナリの起動・バージョン確認が成功した。Windowsのチェックアウト時に生じた改行変換は、GoファイルをLFに固定して解消した。このCIをリリースの前提条件にしている。arm64での実行と、実際のGoogleアカウントを使う認証ストア連携は未検証である。

再測定する場合は次を使う。CPU・メモリプロファイルも一時ディレクトリへ取得済みである。

```sh
go test -run '^$' -bench 'BenchmarkPicker(Cold)?Startup' -benchmem -count 3 ./pkg/tui
go test -run '^$' -bench BenchmarkQuotaFetchLatency -benchmem -benchtime=600ms -count 3 ./pkg/quota
```

## 最適化前の参考値

2026年11月17日、Linux amd64、Go 1.27.4、Intel Core i9-13900Tで、アカウント選択画面のモデル初期化を3回ずつ測定した。ネットワーク通信は含まず、各アカウントのクォータが保存されたJSONキャッシュを読む条件である。描画時間やCLI起動全体の時間は含まない。同じ環境でビルドも実行していたため、数値は比較用の参考値とする。

| アカウント数 | 処理時間の中央値 | 1回あたりのメモリ割り当て | 割り当て回数 |
| --- | --- | --- | --- |
| 10 | 0.496ms | 約66.5KB | 255回 |
| 100 | 34.436ms | 約6.02MB | 12,121回 |

メモリは処理中に割り当てたバイト数であり、常駐メモリ量ではない。測定対象は [BenchmarkPickerStartup](../pkg/tui/picker_async_test.go)。同じ条件で再測定する場合は次を使う。

```sh
go test -run '^$' -bench BenchmarkPickerStartup -benchmem -count 3 ./pkg/tui
```

この参考値を測定した時点では、テスト43件と競合検査が通過していた。Linux・macOS・Windowsのamd64/arm64向けビルドも成功していたが、macOSとWindowsでのテスト実行、実際のGoogle APIへの接続性能は未検証だった。

## 当初の実装順と目標

次表は着手時の作業順と目標である。実装後の結果は前節に示した。優先度P0は認証情報の保持と処理停止の制御、P1は性能とブリッジの安定動作、P2はOSごとの継続検証を示す。

| 順序・優先度 | 変更内容 | 予測される効果 | 完了条件の案 |
| --- | --- | --- | --- |
| 1・P0 | CLIをアカウント・プロキシ・ブリッジのコマンドに分割し、認証ストア、HTTPクライアント、プロセス実行を外部から渡せる構造にする | コマンド追加や障害対応時に変更する範囲が分かりやすくなる。テストで実際の認証ストアや外部通信を使わずに済む。速度改善率は設定しない | コマンド名・引数・終了コードを維持。テストのためにHTTPのグローバル変数を書き換える処理をなくす |
| 2・P0 | ログイン・切替・ログアウトをプロセス間ロックで保護し、保存失敗を返す。ライブ認証、プロファイル、選択中マーカーの更新順と復旧方法を定める | 同時操作による認証情報の取り違えや、「成功」と表示したのに保存されていない状態を防ぐ。故障率の削減幅は未測定 | 同時ログイン、容量不足、アクセス拒否、Keychain/Credential Manager失敗を再現。失敗時も元の認証情報を回復できる |
| 3・P1 | クォータキャッシュを画面起動時に一度だけ読み、各アカウントへ配る。書き込みはプロセス間ロックと一時ファイルへの保存・置換で保護する | 100件時のJSON読み込み・解析を100回から1回へ削減。全件解析の仕事量はアカウント数に対する二乗増加から線形増加へ変わる | 同じベンチマークで100件時1〜5ms、割り当て0.1〜0.5MBを目標とする。複数プロセスの更新で他アカウントのキャッシュを消さない |
| 4・P0/P1 | HTTP処理に共通のcontextと期限を渡す。クォータ取得の並行数を制限し、同じアカウントへの重複取得をまとめる。再試行は期限内の一時障害に限定する | OAuth更新で無期限に待つ状態をなくす。独立した3回のAPI取得を並行化できれば、各100msの模擬条件では通信待ちが約300msから約100msに近づく | 全体の期限15秒、同時HTTP処理数4を初期案とする。中断時の終了、一時障害、429、期限切れを模擬サーバーで検証し、値は実測後に調整する |
| 5・P1 | ブリッジの接続数を追跡し、CONNECTの両方向転送に半切断処理と接続期限を設ける。プロキシ設定変更の反映方法を定める | 切断後に残る接続・goroutineと、通信中のブリッジ終了を防ぐ。長時間利用時の効果を検証する | 接続・切断を1,000回繰り返して、接続数が元に戻ることを確認。送受信が一方だけ終了する場合、設定変更、待機中の停止も検証する |
| 6・P2 | CIでLinux・macOS・Windowsのテストを実行し、リリース用バイナリの起動とバージョンを検査する | OS固有のパス、ファイル置換、認証ストアの不具合をリリース前に検出しやすくなる。性能改善率は設定しない | 各OSのamd64でコマンドと一時ファイルのテストが成功する。認証ストアはモックと専用環境で検証。arm64はビルド検査と実行検査を区別して記録する |

順序3の時間・メモリは達成目標であり、実測した改善効果ではない。現在の100件時の中央値と比べると、時間は約85〜97%、割り当て量は約92〜98%の削減を狙う。実装ではキャッシュ全体の解析をアカウントごとに繰り返す処理を除去した。

順序4の約3倍の短縮は、独立した3リクエストの所要時間が同じ場合の理論値である。Google APIの待ち時間、接続の再利用、同時実行の制限によって実際の効果は変わる。期限を短くすると低速回線で失敗が増えるため、固定値だけで運用せず調整可能にする。

## 測定と回帰確認を各変更の完了条件にする

変更前後は同じ端末、同じGoバージョン、同じデータで測定し、並行ビルドを止める。キャッシュあり・なしの条件を分け、10件と100件に加えて、必要に応じて1,000件でも測る。平均だけでなく、処理時間の分布、割り当て量、HTTPリクエスト数、接続数を確認する。

各変更で関連テストと `go test -race ./...` を実行する。性能変更では `-benchmem` とCPU・メモリプロファイルを比較し、処理時間が短くても認証情報の保持や停止操作が退行した変更は採用しない。OS固有の結果は、クロスビルド成功と実機テスト成功を分けて残す。

今後は実APIでの待ち時間と、認証ストア連携を専用環境で確認する。新たな最適化は、これらの結果から負荷の大きい処理を特定して進める。
